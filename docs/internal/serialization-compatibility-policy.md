# Serialization Compatibility Policy

## Goals

Every public wire format in this workspace is versioned and domain-tagged
on purpose: a decoder should never silently misinterpret bytes meant for a
different type, and a wire-shape change should never be reused under the
same version. This document states the rules that already govern the
existing formats explicitly, so a future change follows them rather than
improvising.

## Domain tags and versions

`phantom_utils::serialization::{DomainTag, Version, SerializationHeader}`
is the shared mechanism four crates build their own format on
(`phantom-lattice`, `phantom-schemes`, `phantom-bootstrapping`,
`phantom-circuits` - see each crate's own `serialization.rs`): an 8-byte
ASCII domain tag plus a `u16` version, written first and checked by
`SerializationHeader::read_expected` before anything else is read.

- **A domain tag identifies a type, forever.** Once a domain tag (e.g.
  `BGVCTXT1`) has shipped, it must keep decoding to the same semantic type
  with the same wire shape for that version. A genuinely new type gets a
  new domain tag - domain tags are never reused for a different or
  incompatible type, even across major version bumps.
- **A version identifies a wire shape.** If a type's own encoding needs to
  change shape (a new field, a reordered field, a different integer width),
  bump that domain's own `Version` constant. The old version number must
  never be reinterpreted as the new shape - `read_expected` checks for an
  *exact* match and rejects anything else, including a technically-still-
  parseable older payload. There is no format negotiation or forward/
  backward-compatible decoding anywhere in this workspace today: an old
  payload under a new version fails cleanly with `UnsupportedVersion`
  rather than being silently upgraded. If a future need for real migration
  support arises (reading old data forward into a new version), that is a
  deliberate new feature to design, not something to retrofit into
  `read_expected`'s own current all-or-nothing check.
- **`phantom-multiparty`'s own three wire formats are a deliberate
  exception**, not an oversight: `common::shares::Share` and
  `vss::share::{VssCommitmentSet, VssShare}` predate the shared
  `SerializationHeader` and use their own hand-rolled magic-byte tag
  (`PMSHR1`, `PMVSC1`, `PMVSH1`) with no separate version field. These are
  short-lived protocol messages exchanged within one session, not
  long-term-stored data - the same domain-identifies-a-type rule above
  still applies to their own tags, but there is no version field to bump
  if their own shape ever needs to change; that would mean minting a new
  tag instead (e.g. `PMSHR2`).

## Testing every format

Every serialized type pair gets, at minimum (`tests/phase17_serialization.rs`
in each of the four `SerializationHeader`-based crates,
`tests/serialization.rs` in `phantom-multiparty` - Workstream 8):

1. **A round-trip test** - `decode(encode(value)) == value` (or the
   equivalent field-by-field check for a type that can't derive
   `PartialEq` in full).
2. **A golden-byte test** - a fixed, previously-generated encoding checked
   into the test file, asserted in both directions. This is the one thing
   a round-trip test structurally cannot catch: a round trip only proves
   this build's own encoder and decoder still agree with *each other*,
   never that the wire shape has drifted from what's already out there.
   Golden bytes are always generated by actually running the encoder once
   (a throwaway script, never hand-computed) before being pasted into the
   test.
3. **Domain-mismatch and version-mismatch rejection** - another type's own
   bytes fed to this type's decoder, and this type's own bytes with a
   corrupted version byte, both asserted to fail with the specific expected
   error variant (`UtilsError::InvalidDomain`/`UnsupportedVersion`), not
   just `.is_err()`.
4. **A truncation-rejection test** - a valid encoding with its last byte(s)
   removed still fails cleanly.
5. **A `proptest` property that decoding arbitrary bytes never panics** -
   `decode_x(&arbitrary_bytes)`, ignoring the `Result`; `proptest` itself
   treats a panic inside the test body as a failure, so this is the direct
   way to enforce "a decoder always fails gracefully, never panics" against
   a much wider input space than any fixed set of hand-picked malformed
   payloads would cover.

## Secret-bearing types stay non-serializable by default

No `SecretKey` (or any other raw cryptographic secret - an RLWE secret
scalar, a per-participant multiparty secret share of the kind
`phantom-multiparty`'s six real protocols keep strictly local) gets an
`encode`/`decode` pair in any `serialization.rs` without a deliberate
security review and a corresponding `SECURITY.md` update. There is
currently no such pair anywhere in this workspace - grep `serialization.rs`
in every crate for `SecretKey` before assuming otherwise, since this is a
standing invariant to check, not a one-time fact.

`phantom-multiparty::vss::VssShare` is not an exception to this rule so
much as a different category entirely: it *is* a secret value (a
participant's own Shamir/Pedersen evaluation), and it *does* have a real,
reviewed `encode`/`decode` pair - because controlled transmission between
a specific dealer and a specific recipient, verified against a public
Pedersen commitment before the recipient ever trusts it, is VSS's whole
purpose. That is a deliberate protocol design, already reviewed as part of
Workstream 7's own VSS work, not a gap this policy is flagging.

## Adding a new serialized type

1. Pick a domain tag that doesn't collide with an existing one (grep every
   crate's own `serialization.rs`/wire module for the exact 8 bytes first).
2. Start at `Version::new(1)` for that domain.
3. Write the round-trip, golden-byte, domain/version-mismatch, truncation,
   and `proptest` decode-never-panics tests described above before
   considering the type's serialization support done.
4. If the type carries or could carry secret material, read the section
   above first and get it reviewed explicitly - don't add the pair as a
   convenience.
